Implementation Notes

Issue #0083 — Durable provider jobs and restart recovery — 2026-08-23

Design Decisions

Decision Separate durable job and attempt facts

Choice: Store one idempotent provider_job row plus a bounded provider_job_attempt ledger. Rationale: The job is the reconstructible projection, while attempts retain crash/retry evidence without creating a WorkTask or Automation state machine.

Decision Hash leases and never persist request bodies

Choice: Persist only a 64-character request digest and SHA-256 lease-token hash; the raw token stays with the worker. Rationale: Restart recovery and stale-worker rejection remain durable without storing credentials or provider payloads.

Decision SQLite facts outrank refresh events

Choice: Startup invokes expired-lease recovery, and claim/submit operations reconstruct from SQLite. Rationale: Missed or reordered EventEmitter refresh hints cannot lose job state.

Deviations

Deviation Recovery marks the last running attempt interrupted

Spec: Recover running jobs after a crash. Implementation: An expired lease becomes interrupted in the attempt ledger and is requeued until the bounded budget is exhausted. Reason: The external idempotency key provides the at-least-once safety boundary for a replay.

Deviation Busy retry is explicit at the repository boundary

Spec: Durable repository behavior under SQLite. Implementation: SQLite lock errors receive bounded linear backoff, and a lost claim race is retried rather than treated as “no work.” Reason: Production uses a pooled SQLite connection and concurrent workers must not lose capacity.

Tradeoffs

Tradeoff Provider idempotency over exactly-once mutation

Exactly-once external mutation cannot be guaranteed across a process crash. The repository preserves one stable key and requires adapters to send it to the provider, giving safe at-least-once replay without pretending the network is transactional.

Tradeoff Bounded diagnostics over raw provider errors

Raw provider messages are more verbose but can contain payloads or credentials. Capped control-free diagnostics and marker redaction keep persisted facts safe; later operations can add structured safe error codes.

Open Questions

Follow-up Adapter reconciliation semantics

Issue-084 and later provider issues should define how an adapter queries the provider with the stable idempotency key after an uncertain external mutation, before issuing a fresh mutation.
