Implementation Notes

Issue #0084 — Plugin configuration, health and job operations — 2026-08-23

Design Decisions

Decision Persisted projections are authoritative

Choice: Build the operations response from the stored context configuration, provider health checks and provider-job rows. Rationale: EventEmitter notifications are refresh hints; missed or reordered events cannot erase durable state.

Decision One command core serves both transports

Choice: Tauri and Axum call the same context_plugin_operations_core function. Rationale: Redaction, bounded limits and projection semantics stay identical across desktop and server modes.

Decision Redact at the projection boundary

Choice: Return only safe endpoint metadata, environment-variable configured booleans and digest prefixes; never return secret values, request bodies or lease tokens. Rationale: The renderer can show useful operations state without becoming a provider or credential boundary.

Deviations

Deviation Existing health checks remain the compatibility path

Spec: Plugin operations must not make renderer-to-provider calls. Implementation: The backend reuses the existing provider health abstraction, while static registry plugins use registry-owned health and the frontend only consumes the projection. Reason: This preserves existing provider behavior and keeps network access out of the renderer.

Deviation Attempt history is bounded in the UI projection

Spec: Expose job operations and recovery facts. Implementation: At most 100 jobs and five attempts per job are projected. Reason: Operations views must remain predictable even when a database contains a large retry history.

Tradeoffs

Tradeoff Safe hashes over actionable payload visibility

Showing request bodies or raw idempotency keys would improve debugging but risks credential and content leakage. The UI exposes only stable hash prefixes and status/error projections, leaving detailed payload inspection to controlled backend diagnostics.

Tradeoff Small operations panel over a new state store

The Context page consumes the existing API, Tabs, Card, Metric, Badge and Empty patterns instead of introducing another frontend state machine. This keeps parity cheap while retaining empty, degraded and last-good states.

Open Questions

Follow-up Adapter reconciliation after uncertain mutation

Future provider adapters should define how an uncertain external mutation is reconciled with the durable idempotency key before a retry is issued.
