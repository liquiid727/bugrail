# SpecOS 产品需求文档

> 文档定位：长期产品目标  
> 产品载体：Code: Bugrail  
> 目标用户：使用 AI 编程工具的软件开发者  
> 状态：方向稿，后续功能需要分别经过 PRD、设计、Spec 和验证  
> 说明：本文描述 SpecOS 最终希望解决的问题和完整能力范围，不冻结未来实现接口，也不等同于当前版本的交付清单。

## 1. SpecOS 要解决什么问题

开发者已经可以同时使用 Codex、Claude 等编程 Agent，但任务一旦变复杂，仍然需要自己承担大量协调工作：

- 反复向不同 Agent 解释项目背景和当前目标；
- 判断应该使用哪个供应商、模型、提示词和 Skill；
- 把大任务拆开，再决定哪些部分可以并行；
- 检查 Agent 是否改对了代码、有没有漏掉测试；
- 在多个会话、分支和 Worktree 之间传递进度；
- 记住上一次为什么失败，下一次不要重复犯错。

这些工作目前大多存在于聊天记录和开发者的脑子里。Agent 可以完成一次代码修改，却不了解一次完整交付需要经过哪些步骤，也不能独立证明自己的结果可以合并。

SpecOS 希望让开发者拥有一组可以配置、分工和协作的 AI 工程专家。开发者只需要说明想完成什么，系统负责准备上下文、安排执行、检查结果并保留过程记录。任何自动决策都可以关闭，开发者始终可以自己指定 Agent、模型和执行方式。

一句话概括：

> SpecOS 帮助一个开发者管理多个 AI 工程专家，并把一次代码修改变成一项可检查、可接管、可追踪的工程交付。

## 2. 产品边界

### 2.1 SpecOS 与 Code: Bugrail 的关系

Code: Bugrail 提供开发工作台和 Agent 运行环境，包括：

- 项目与工作区；
- 对话和 Agent Session；
- Git 与 Worktree；
- Codex、Claude 及其他 Agent 的接入；
- 桌面端、Web 端和远程访问；
- 文件、终端、Diff 等开发工具。

SpecOS 在这些能力上增加工程任务管理：

- 保存需求、任务、验收条件和执行结果；
- 管理不同用途的 Agent Profile；
- 为任务选择 Agent、模型、Skill 和知识；
- 准备每次执行实际需要的上下文；
- 拆分和调度相互依赖的任务；
- 运行测试、审查和人工确认；
- 记录每次执行，并从重复结果中提取经验。

SpecOS 不重新开发编辑器、终端、Git 客户端或大模型运行时。它调用 Code: Bugrail 已有能力，并为一次工程交付增加计划、控制和验证。

### 2.2 谁使用 SpecOS

SpecOS 的直接用户是开发者，不要求用户先组建真实的软件团队。

一个开发者可以配置多个 Agent Profile。例如：

- 后端专家：熟悉项目的服务端结构、数据库规范和 API 规则；
- 前端专家：熟悉组件库、交互规范和浏览器验证方法；
- 测试专家：专门补充测试、复现缺陷和检查边界条件；
- 安全审查专家：关注权限、密钥、输入校验和依赖风险；
- 集成专家：负责合并多个 Worktree 并处理冲突。

这些 Agent Profile 可以接入不同供应商和模型，也可以拥有不同的提示词、Skill、知识、工具和权限。它们是开发者配置的虚拟专家，不代表真实组织中的岗位。

## 3. 产品目标

### 3.1 让复杂任务更容易控制

开发者提交一个任务后，可以看到系统准备了哪些上下文、选择了哪些 Agent、拆出了哪些子任务，以及每个子任务现在处于什么状态。

### 3.2 让执行结果可以验证

Agent 说「已经完成」只代表执行结束。是否可以合并，要由验收条件、构建、测试、审查和必要的人工批准共同决定。

### 3.3 让自动化保持可选

Agent 自动选择、模型路由、任务拆分、并行执行和经验注入都应提供开关。关闭自动选择后，开发者可以手工指定 Agent、模型、Skill、上下文和执行步骤。

### 3.4 让项目经验可以复用

系统记录成功和失败的执行过程。只有反复出现并经过验证的做法，才会成为可复用的规则、模式或 Skill 候选。

## 4. 一次任务怎样完成

下面以「给支付模块增加部分退款，并在订单详情显示退款记录」为例。

1. 开发者输入需求，也可以关联已有 PRD、设计或 Spec。
2. 系统判断任务涉及支付、数据库、后端、前端和测试，提示这是一项高风险的跨模块修改。
3. 系统建议验收条件和任务拆分，开发者可以确认或调整。
4. 如果自动选择已开启，系统推荐后端、前端、测试和审查 Agent；如果已关闭，开发者自己指定。
5. 系统为每个任务准备上下文，包括目标、相关文件、符号、测试、项目规则和历史决策。
6. 可并行的任务进入不同 Worktree 和 Session，互不覆盖代码。
7. 每个 Agent 完成后提交结构化结果，包括改了什么、做了什么决定、还剩什么风险、运行了哪些验证。
8. 集成步骤合并各项修改，处理冲突，并运行跨模块测试。
9. 质量检查根据风险执行构建、测试、审查和安全检查。支付等高风险修改需要开发者确认后才能合并。
10. 完成后生成本次任务的执行记录。后续任务可以引用其中经过确认的事实和决策。

开发者可以在任何一步暂停、取消、重试、替换 Agent、修改模型、补充上下文或进入 Session 接管操作。

## 6. 用户故事

### US-001：配置一个项目专家

作为开发者，我希望把供应商、模型、提示词、Skill、项目知识和权限保存成一个 Agent Profile，以便在多个任务中重复使用，而不用每次重新配置。

完成时应满足：

- Agent Profile 可以创建、复制、修改、禁用和版本化；
- Profile 能清楚显示它可以使用的模型、工具、知识和权限；
- 密钥只保存在受保护的凭据存储中；
- 修改 Profile 不会悄悄改变正在运行的任务。

### US-002：把任务交给合适的专家

作为开发者，我希望输入一个工程任务后得到 Agent、模型和执行计划建议，以便少做重复的选择工作。

完成时应满足：

- 自动选择可以按项目或单次任务开启、关闭；
- 系统能够解释推荐依据；
- 开发者可以在执行前修改任何推荐结果；
- 关闭自动选择后，系统不会替用户更换 Agent 或模型。

### US-003：查看并控制执行过程

作为开发者，我希望看到任务依赖、Session、Worktree 和实时状态，以便发现问题时立即介入。

完成时应满足：

- 每个执行节点都能打开对应 Session、Worktree、上下文和 Diff；
- 用户可以暂停、取消、重试、重新分配或手工接管；
- 并行任务不会写入同一个工作区；
- 阻塞状态会说明正在等待什么。

### US-004：确认结果是否可以合并

作为开发者，我希望系统根据验收条件、测试和独立审查判断任务是否完成，以免把 Agent 的自我汇报当成可靠结论。

完成时应满足：

- 必要检查未通过时，任务不能显示为可合并；
- 每条验收条件都能找到相应证据或明确显示缺失；
- 高风险操作必须等待人工确认；
- 开发者可以查看原始命令输出和审查意见。

### US-005：让项目逐渐减少重复错误

作为开发者，我希望系统记录经过确认的项目事实、决定和失败教训，以便后续 Agent 使用相关经验。

完成时应满足：

- 单次运行只能产生候选经验，不能直接修改正式规则或 Skill；
- 经验必须记录来源、适用范围和置信度；
- 冲突内容不能静默覆盖；
- 开发者可以随时停用、修改或删除自动注入的记忆。

## 7. 产品规则

这些规则用于约束后续功能设计。

1. **自动功能必须可以关闭。** 用户可以改用手工选择和手工执行。
2. **每次自动选择都要说明原因。** Agent、模型、上下文和质量检查不能只给出黑盒结果。
3. **Agent 不能证明自己已经完成。** 完成状态由独立验证和用户规则决定。
4. **高风险操作不允许静默执行。** 合并、发布、部署、生产数据库和密钥访问需要明确权限。
5. **上下文按任务准备。** 系统不应把全部项目资料无差别塞给每个 Agent。
6. **执行任务默认隔离。** 一个任务默认拥有自己的 Worktree 和 Session。
7. **重要结果要保存为可查询记录。** 需求、任务、运行、审查、测试和决定不能只留在聊天里。
8. **学习需要多次证据。** 一次成功不能自动生成正式 Skill，一次失败也不能自动推翻项目规则。
9. **开发者始终可以接管。** 暂停、取消、重试、替换和手工处理是正式能力。
10. **实现可以演进。** 本文约束产品方向，不提前冻结尚未验证的模块接口。

## 8. 功能需求

- FR-1：系统必须允许开发者连接多个 Agent 或模型供应商。
- FR-2：系统必须允许开发者创建包含模型、提示词、Skill、知识、工具和权限的 Agent Profile。
- FR-3：系统必须允许开发者开启或关闭 Agent 与模型的自动选择。
- FR-4：自动选择关闭时，系统必须使用开发者明确指定的 Agent 和模型。
- FR-5：自动选择开启时，系统必须展示推荐结果和推荐理由。
- FR-6：系统必须允许开发者在执行前修改任务拆分、Agent、模型和验证计划。
- FR-7：系统必须为每次执行生成独立且可检查的上下文包。
- FR-8：上下文中的每一项必须记录来源和选择理由。
- FR-9：系统必须为相互隔离的任务分配独立 Worktree 和 Session。
- FR-10：系统必须按照任务依赖和并发限制安排执行顺序。
- FR-11：系统必须允许开发者暂停、取消、重试、重新分配和接管任务。
- FR-12：Agent 完成任务后必须提交改动、决定、风险和验证结果。
- FR-13：系统必须保存构建、测试和审查的原始结果。
- FR-14：所有必要检查通过之前，系统不得把任务判定为完成。
- FR-15：高风险合并、发布和敏感权限操作必须支持人工确认。
- FR-16：系统必须记录一次运行使用的 Agent、模型、上下文、工具、改动、耗时、成本和结果。
- FR-17：系统必须允许开发者从任务状态跳转到对应 Session、Worktree、Diff 和验证证据。
- FR-18：系统必须允许用户检查、修改和删除项目记忆。
- FR-19：系统不得根据单次运行自动创建或启用正式 Skill。
- FR-20：系统必须为自动形成的规则、模式和 Skill 保留来源与验证记录。

## 9. 交互要求

### 9.1 主要入口

开发者的第一入口是「任务」，不是 Agent 配置页或流程编辑器。

任务页至少要回答：

- 我让系统做什么；
- 系统准备怎么做；
- 现在由谁执行；
- 使用了哪些上下文；
- 哪些步骤已经完成；
- 哪些检查通过或失败；
- 现在是否需要我处理。

### 9.2 任务关系图

复杂任务可以用关系图展示，但简单任务不应被迫进入多节点流程。每个节点至少显示状态、Agent、模型、Session、Worktree、耗时和验证结果。

### 9.3 运行详情

运行详情需要同时服务两个场景：

- 开发者想快速判断任务是否正常；
- 开发者排查为什么选错了 Agent、漏了上下文或没有通过测试。

因此详情页既要有简短状态摘要，也要能展开查看上下文、工具调用、文件改动、命令输出和失败原因。

### 9.4 必须覆盖的界面状态

所有主要页面和操作都需要定义：

- 空状态：还没有任务、Agent、模型连接或运行记录；
- 加载状态：正在索引项目、准备上下文或等待 Agent 响应；
- 成功状态：任务完成且验证通过；
- 失败状态：连接失败、任务失败、验证失败或权限被拒绝；
- 等待状态：等待依赖、资源或人工确认；
- 部分成功：部分子任务完成，但整体尚不可合并。

## 10. 技术方向

下面内容用于说明产品能力之间的关系，不是已经冻结的实现接口。

### 10.1 工程记录

PRD、设计、Spec、Issue、运行、审查、测试、决定和发布记录需要有稳定标识和引用关系。文件可以作为人可读来源，数据库或索引用于查询。后续实现应避免出现两份互相冲突的权威数据。

### 10.2 Agent 运行适配

上层任务流程不应绑定某一个 Agent CLI。Code: Bugrail 可以通过 ACP 或其他适配方式管理 Session 和任务，Git Diff 与 Worktree 状态仍以本地 Git 结果为准。

### 10.3 代码理解

代码理解不能只依赖语义搜索。符号、引用、依赖、测试、Git 历史和修改影响需要组合使用。不同语言和项目可以采用不同实现。

### 10.4 质量检查

构建、Lint、类型检查、测试和审查需要使用统一结果格式，但具体命令由项目配置。失败结果要保留原始输出，不能只记录「失败」。

### 10.5 数据与权限

项目资料默认保存在用户控制的位置。供应商密钥不进入任务记录、上下文包或日志。任何涉及网络、密钥、生产数据和部署的能力都要单独授权。

### 10.6 可替换实现

Agent Runtime、代码索引、上下文解析、存储、审查、记忆和模型路由可能需要替换实现。只有出现第二种真实实现或明确外部接入需求时，才把对应边界稳定为公开插件接口。

## 11. 演进顺序

这份长期 PRD 不直接生成一整套冻结 Spec。每一阶段开始前，需要根据当时的 Code: Bugrail 能力重新写阶段 PRD、设计和验收标准。

### 阶段一：可配置的专家

- 连接多个供应商和模型；
- 创建 Agent Profile；
- 配置提示词、Skill、知识、工具和权限；
- 支持自动选择开关与手工指定；
- 能在 Code: Bugrail 中启动并接管一次任务。

完成标志：开发者可以稳定地把同一类任务交给一个配置好的专家，并知道实际使用了哪些配置。

### 阶段二：可靠的单任务交付

- 保存任务目标和验收条件；
- 生成并检查上下文包；
- 使用独立 Worktree 和 Session；
- 执行构建、测试和独立审查；
- 生成可查看的运行记录。

完成标志：一项真实工程任务可以从输入走到验证完成，失败时能够说明卡在哪一步。

### 阶段三：多个专家协作

- 拆分有依赖关系的子任务；
- 自动推荐多个 Agent；
- 并行执行互不冲突的任务；
- 结构化交接和集成；
- 用任务关系图查看和控制全过程。

完成标志：一个跨前后端的真实任务可以由多个 Agent 协作完成，开发者能够在任意节点接管。

### 阶段四：代码理解与风险控制

- 建立代码符号、引用和依赖索引；
- 自动选择相关上下文；
- 分析修改影响；
- 按风险增加专项审查、测试和人工确认；
- 比较不同 Agent 和模型的效果。

完成标志：系统能够解释「为什么选择这些文件、Agent 和检查项」，并减少因上下文缺失造成的返工。

### 阶段五：项目记忆与受控优化

- 从运行中提出经验候选；
- 识别重复成功或重复失败的模式；
- 验证 Skill 候选；
- 根据历史结果优化 Agent、模型和上下文选择；
- 识别过期或冲突的知识。

完成标志：优化结果能够通过历史对比或影子运行证明有效，开发者可以撤销任何自动调整。

## 12. 不在范围内

- 重新开发完整代码编辑器、终端或 Git 客户端；
- 自研基础大模型或替代 Codex、Claude 等 Agent Runtime；
- 默认把所有任务拆给多个 Agent；
- 在没有人工规则的情况下自动合并或部署高风险修改；
- 根据一次运行自动生成正式 Skill；
- 无限制地跨项目共享代码、记忆、密钥或内部知识；
- 为了插件化而提前抽象所有模块；
- 承诺任何供应商和模型永久可用；
- 在长期 PRD 中提前冻结尚未经过真实任务验证的 API。

## 13. 如何衡量产品是否有效

### 13.1 交付效率

- 从创建任务到验证完成所需的时间；
- 开发者为补充背景和上下文进行的人工操作次数；
- 可以安全并行执行的任务比例；
- 失败后从检查点恢复而不是重新开始的比例。

### 13.2 交付质量

- 首次执行后通过全部必要检查的任务比例；
- 审查一次通过率；
- 验收条件拥有代码、测试或审查证据的比例；
- 合并后出现回归的比例。

### 13.3 Agent 使用效果

- 不同 Agent、模型和 Skill 在各类任务上的成功率；
- 平均耗时、Token 和估算成本；
- 自动推荐被开发者接受、修改或拒绝的比例；
- 因上下文缺失、选择错误或权限不足导致的失败比例。

### 13.4 学习效果

- 经过开发者确认后被再次使用的项目经验比例；
- Skill 候选通过验证的比例；
- 使用新 Skill 后成功率、耗时或成本的变化；
- 被标记为过期、冲突或低价值的知识数量。

每个阶段 PRD 需要根据现有基线设置具体目标值。长期 PRD 只保留指标定义，避免在没有数据时给出虚假数字。

## 14. 最终验收场景

当开发者提出一个跨模块、高风险的真实需求时，完整形态的 SpecOS 应当做到：

1. 保存原始需求并提出可编辑的验收条件；
2. 给出任务复杂度、影响范围和风险判断；
3. 在自动模式下推荐合适的 Agent、模型、Skill 和执行计划；
4. 在手动模式下完全尊重开发者指定的 Agent 和模型；
5. 为每个任务准备来源可查的上下文；
6. 在独立 Worktree 和 Session 中执行可并行的任务；
7. 让每个 Agent 提交结构化交接结果；
8. 合并修改并执行必要的构建、测试和独立审查；
9. 在高风险操作前等待开发者确认；
10. 让每条验收条件都能关联到代码、测试或审查证据；
11. 保存完整运行记录，并明确区分成功、失败和人工接管；
12. 从运行中提出经验候选，但不未经确认修改正式规则。

如果开发者无法理解系统为什么做出某项选择，无法在执行中接管，或者无法根据证据判断任务是否完成，这次交付就不算达到 SpecOS 的最终目标。

## 15. 仍需在阶段 PRD 中回答的问题

- Code: Bugrail 暴露哪些 Agent 和 Session 控制能力，哪些需要新增适配层；
- 第一批正式支持哪些供应商、模型和操作系统；
- Agent Profile 的全局配置与项目配置如何继承；
- 自动选择开关的默认状态和首次引导方式；
- 哪些任务允许自动拆分，哪些任务必须先让开发者确认；
- 项目资料采用文件、SQLite 或两者组合时，哪一份是权威来源；
- 如何定义可恢复检查点，以及不同 Agent Runtime 支持到什么程度；
- 哪些数据可以用于跨项目评估，哪些必须始终留在单个项目中；
- 哪些插件能力需要公开给第三方，公开的依据是什么。

## 16. 名词说明

| 名词 | 本文含义 |
|---|---|
| Agent | 实际执行任务的 Codex、Claude 或其他编程 Agent |
| Agent Profile | 开发者保存的一套专家配置，包含角色、模型策略、提示词、Skill、知识、工具和权限 |
| Skill | 可复用的任务处理步骤和说明 |
| 工程资料 | PRD、设计、Spec、Issue、运行、审查、测试、决定等可保存和查询的记录 |
| 上下文包 | 一次运行实际提供给 Agent 的目标、代码、规则、测试和历史决定 |
| Worktree | 为一个任务隔离出来的 Git 工作区 |
| Session | 一次 Agent 对话和执行过程 |
| 任务关系图 | 展示子任务依赖、并行关系和状态的视图 |
| 质量检查 | 构建、Lint、类型检查、测试、审查和人工确认等完成条件 |
| 运行记录 | 一次执行使用的输入、配置、工具、改动、验证、成本和结果 |
| 项目记忆 | 经过来源记录和用户确认，可供后续任务使用的事实、决定、规则或失败教训 |
