Implementation Notes

Issue #0082 — Independent plugin contracts and shared AssetRef — 2026-08-23

Design Decisions

Decision Separate typed plugin contracts

Choice: Memory, Wiki, CodeGraph and Skill each expose their own asset, adapter and operation contract. Rationale: This keeps capability surfaces explicit and prevents a catch-all adapter from becoming a cross-plugin dependency.

Decision Vendor-neutral, kind-checked context envelope

Choice: Plugin results enter the Context pipeline through AssetRef, scope/provenance metadata and kind-specific conversions. Rationale: Context can apply its existing budget, deduplication and provenance rules without exposing vendor DTOs.

Decision Static registry owns construction and health

Choice: Manifests are validated in a complete first pass, then adapters are constructed from a static allowlist; health projections come from the registry. Rationale: Invalid configuration cannot cause partial construction, and callers cannot select arbitrary implementations.

Deviations

Deviation Production non-Memory adapters remain foundation stubs

Spec: Establish contracts and static selection. Implementation: Deterministic adapters exercise all four contracts; production selection currently validates manifests and keeps the existing Memory implementation authoritative. Reason: External Wiki, CodeGraph and Skill operations are explicitly deferred to later issues.

Deviation Memory remains behind the existing registry

Spec: Preserve memory::MemoryProvider. Implementation: Memory health still delegates to memory::AdapterRegistry, while the new registry owns the non-Memory foundation. Reason: This avoids changing the TencentDB runtime contract in Issue-082.

Tradeoffs

Tradeoff Static allowlist over dynamic loading

Dynamic loading could add providers without a rebuild, but would weaken validation and deployment safety. The static allowlist matches the non-goal and keeps registry behavior auditable.

Tradeoff Typed conversions over a generic result trait

A generic trait would reduce boilerplate, but permits accidental cross-kind results. Separate conversions make invalid asset kinds fail at the contract boundary.

Open Questions

Follow-up External adapter implementations

Later Wiki, CodeGraph and Skill issues should confirm each provider's static adapter configuration and durable job behavior without widening the shared contract.
